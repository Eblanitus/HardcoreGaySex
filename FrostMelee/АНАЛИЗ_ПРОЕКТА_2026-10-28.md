# Анализ проекта FrostMelee

Дата: 28.10.2026. Ветка: `arena/be992d46-hardcoregaysex` (от `e69fa8a`).
Объект: `FrostMelee/` — мод tModLoader 1.4 (net8.0), часть серии HardcoreMelee.

---

## 0. Коротко

Проект вырос из «переделки Ледяной косы» в полноценный мод: **64 `.cs`, 17 839 строк
(13 617 кода, 2 544 комментария), 8 подсистем, 18 снарядов, 9 ModPlayer, 8 ModSystem,
пять переработанных ванильных оружий плюс два собственных предмета**. Архитектурное
ядро (общая геометрия оружия из CPU-масок + генератор + тесты) сделано на уровне,
который выше среднего по модам.

Три главных риска сейчас:

1. **Производительность в бою.** Визуал огня и приманка построены на полных проходах
   по массивам `Main.dust` (6 000) и `Main.projectile` (1 000) из кадровых/потиковых
   хуков. На «Фростбранде» в толпе это N×12 000 проверок за тик.
2. **Сетевая модель неполная.** Шкала Frost синхронизирована и защищена, а заряд
   карамельки, полировка мечей и токены броска — нет. Заряд карамельки на выделенном
   сервере вообще не расходуется у клиентов (см. F7).
3. **Техдолг репозитория.** 21 `.bak`, 21 файл `bin/obj` (в одном — абсолютные пути
   `C:\Users\user`), два `.tmod`-бэкапа, архив, 836 КБ gif, 22 из 45 PNG не используются,
   английская локализация содержит русский текст, README/планы расходятся с кодом.

Отдельно: **в этом окружении мод не собирался и не запускался** — `dotnet` и tModLoader
отсутствуют. Всё ниже — статический анализ исходников плюс проверки данных (маски,
ассеты, локализация, тесты). Оценки производительности — теоретические, по количеству
итераций, без профилирования.

## 1. Что проверено фактически

| Проверка | Команда | Результат |
|---|---|---|
| Запечённые маски соответствуют PNG | `python tools/generate_collision_masks.py --check` | ✅ `Collision masks match source PNGs` |
| Тесты данных | `python -m unittest discover -s tests -v` | ✅ 4/4 (порог альфы, порядок битов, каждый пиксель, отсутствие GPU-зависимостей) |
| Ссылки на текстуры | скрипт по всем `"FrostMelee/..."` в коде | ✅ 26 путей, все файлы существуют (старый баг «нет папки `Items`» закрыт) |
| Мусорные ассеты | сопоставление PNG ↔ пути/классы | ⚠️ 22 из 45 PNG не используются |
| Локализация en/ru | сравнение ключей hjson + `Language.GetTextValue` | ⚠️ en-US с русским текстом, ru-RU с закомментированными `Configs.*` |
| Сборка C# | `dotnet build` | ⛔️ невозможно: нет `dotnet`, нет tModLoader |

он не установлен — тесты падают на импорте `PIL`. Это стоит закрыть одним
`bootstrap`-скриптом, иначе первый запуск у нового участника выглядит как «тесты красные».

## 2. Что это за проект

### 2.1. Идея

Доктрина серии (HardcoreMelee): оружие сильнее вблизи, единый набор приёмов на всю мили —
**взмах (ЛКМ)**, **тычки (ПКМ зажать)**, **выставленное оружие/встреча (ПКМ тап)**,
**бросок без автовозврата (ПКМ+ЛКМ)**. FrostMelee переносит это на ледяное оружие.

### 2.2. Переработанные ванильные предметы

| Оружие | Движок | Фишка |
|---|---|---|
| Ice Sickle → «Замороженное копьё» | `SicklePlayer` + `Sickle*` | шкала Frost 0..1: тычки/встреча копят, взмах тратит в иней; при ≥0.5 зона удара строится по замороженному спрайту |
| Ice Blade | `SwordPlayer` + `Sword*` | полировка (иней сходит от попаданий, растёт в покое), смена спрайта |
| Frostbrand | `SwordPlayer` | холодное пламя: конечный запас из 5 языков, струя поджигает, тычок забирает горение в урон, вернувшиеся языки-огоньки |
| Candy Cane Sword | `FestiveSwords` + `CandyCaneLure` | брошенный леденец манит врагов на заряде сладости 10 с |
| Christmas Tree Sword | `FestiveSwords` | шаблонные приёмы, своя палитра дуги |
| Ice Boomerang | `BoomerangPlayer` | лёгкие броски, размах, тяжёлый заряжаемый бросок, скольжение по воде |
| Amarok (йо-йо) | `AmarokPlayer` | свой полёт, наводка, круг, нарастающий лёд, противовесы |
| North Pole | `SpearPlayer` | заглушка (TODO), механики нет |

Собственные предметы мода: **Айсберг** (165 урона, глыбы, пост-Плантера) и
**Ледниковый цеп** (дроп ледяных черепах 1/40 после первого мех-босса).

### 2.3. Слои

```
ввод/состояние      SicklePlayer, SwordPlayer, BoomerangPlayer, AmarokPlayer, SpearPlayer
спавн/поведение     SickleArc / SickleStab / SickleBrace / SickleThrow
                    SwordArc / SwordStab / BoomerangLight / BoomerangHeavy
                    GlacialFlail, AisbergChunk, AisbergBlast, IceWaveSpike
геометрия урона     SickleSprite ← WeaponCollisionMasks (запечённые маски, CPU)
визуал               FrostJetFx (пламя, RenderTarget), FlameRibbon, IceRibbon, StabRibbon,
                    FrostTrailSystem, FrostZoneSystem, IceSheetSystem, FrostDrainFx, FrostFlameWisp
интерфейс            SickleUI, SwordUI, YoyoUI, FrostMeleeConfig
сеть                 Mod.HandlePacket (один тип пакета) + SicklePlayer.SendFrost/SyncPlayer
```

Поток одного взмаха (проверено по коду): ванильный `useStyle = Swing` → `SickleGlobalItem.Shoot`
возвращает `false` и спавнит `SickleArcProjectile` (урон = урон предмета × стихия) →
`SicklePlayer.PostUpdate` крутит серп своим слоем, `SickleArcProjectile` бьёт по секторам из
`SickleSprite.GetZone`, `SwordArcProjectile`/`SickleArcProjectile` рисуют ленту вершинным
буфером. Ванильный `UseItemHitbox` глушится (`noHitbox = true`), чтобы не было двойного урона —
это правильное решение и оно единообразно у серпа и мечей.

## 3. Сильные стороны

1. **Геометрия урона.** `WeaponCollisionMasks.Generated.cs` — запечённые alpha-маски +
   генератор + 4 регрессионных теста. Урон считается по пикселям спрайта одинаково на
   сервере и клиенте, без `GetData`/GPU и без зависимости от ресурспаков. Сейчас
   проверено: маски актуальны для 8 профилей (IceSickle, IceBlade, Frostbrand,
   CandyCaneSword, ChristmasTreeSword, Aisberg, LongFrostbrand, CandyGray).
2. **Явная owner-authoritative модель снарядов** и документированные ограничения в
   `NETWORK_STABILIZATION.md` — редкость: обычно сетевые допущения нигде не записаны.
3. **Пакет Frost проверяется на сервере** (длина, отправитель, конечность, диапазон) —
   `FrostMelee.HandlePacket`.
4. **Static-кэши в основном убираются**: `OnWorldUnload`/`Unload` есть у FrostJetFx,
   FrostZoneSystem, FrostTrailSystem, FrostFireSystem, IceSheetSystem, SickleTextures,
   SickleSprite.
5. **Комментарии объясняют «почему», а не «что»** — включая зафиксированные решения
   владельца и отвергнутые варианты. Это сильно снижает риск откатить удачное решение.

## 4. Найденные проблемы

Приоритеты: **P1** — заметно влияет на игру/производительность, **P2** — сеть/совместимость,
**P3** — долг и гигиена.

### 4.1. Производительность

**F1 (P1). Постоянный скан всей пыли каждый кадр — даже когда огня нет.**
`FrostJetFx.RenderFire` вызывается из `Main.OnPreDraw`, и первой строкой зовёт
`CollectVanillaBurnDust()` (`FrostJetFx.cs:1409`), а early-out «нечего рисовать» стоит
**после** него (`:1410`). Внутри — проход по `Main.dust` (6 000), проход по `Main.maxNPCs`
(200) и, если нашлись fallback-враги, **второй** проход по 6 000 пыли (`:620`, `:650`, `:664`).
При дефолтном `FrostFireIntensity = 50` это происходит каждый кадр в любой момент игры,
на любом клиенте с модом.
*Что делать:* сначала дешёвая проверка «есть ли вообще горящий враг / живые частицы»
(флаг, который уже знает `FrostFireSystem`), и только потом сбор пыли; сам сбор — не чаще
раза в 2–3 кадра (кэш по `Main.GameUpdateCount`).

**F2 (P1). Двойной проход по 6 000 слотов пыли на каждого горящего врага каждый тик.**
`CaptureVanillaFrostburnDust` (`FrostJetFx.cs:537`) — MonoMod-хук на
`NPC.UpdateNPC_BuffApplyVFX`. До и после `orig(npc)` идёт полный проход по `Main.dust`
с запоминанием `dustWasActive[]` (6 000 bool) и аллокацией `new VanillaBurnTag` на каждую
новую частицу. Стоимость линейна по числу горящих врагов на экране — то есть ровно
в том сценарии, ради которого мод и сделан: 10 горящих врагов ≈ 120 000 проверок/тик
≈ 7 млн/с, плюс мусор в Gen0.
*Что делать:* метить частицы по индексам, которые вернул спавн (в ванилле пыль
рождается через `Dust.NewDust*`, возвращающий слот), либо проверять «уже размечено»
по счётчику, либо обрабатывать только когда у NPC реально есть `onFrostBurn2` и он
в кадре, и реже, чем каждый тик.

**F3 (P1). `CandyCaneLureNPC.PostAI` — O(активных NPC × 1 000 снарядов).**
`CandyCaneLure.cs:27-46`: для каждого NPC проходится весь `Main.projectile` и на каждом
элементе делает `p.ModProjectile is not SickleThrowProjectile`. При 200 NPC это 200 000
итераций за тик (~12 млн/с) на сервере и в одиночной игре.
*Что делать:* один раз за тик собрать список «приманок» (2–5 штук) в `ModSystem` и
раздавать его NPC; либо держать кэш в `SickleThrowProjectile` через статический счётчик.

**F4 (P2). Логи в горячем пути.** `SwordPlayer.cs:284` пишет строку в `client.log`
на **каждое** успешное попадание Frostbrand/Ice Blade (кулдаун 10 тиков → до 6 записей
в секунду), `SwordPlayer.cs:327` — на каждую смену вида. Это отладка, оставленная в проде;
лог быстро превращается в тысячи строк и мешает разбирать реальные ошибки.
*Что делать:* убрать или закрыть `#if DEBUG` / отдельным `Mod.Logger.Debug`.

**F5 (P2). Пять проходов по `Main.maxProjectiles` за тик.** `SicklePlayer.RefreshThrowTokens`
(`SicklePlayer.cs:554`, зовётся из `PreUpdate:187`), `SwordPlayer.RefreshThrowTokens` (`SwordPlayer.cs:835`), `SwordPlayer.UpdateFlames` (`:173`, цикл на `:176`), `TryConsumeOrbitingFlame`
(`:141`), `LaunchOrbitingFlames` (`:160`), плюс поиск снарядов в слоях
(`SickleSpinSwingLayer.FindArc:32`, `BoomerangPlayer.OwnProjectileActive:73`). В сумме
до ~5–7 тысяч проверок за тик на игрока — не смертельно, но легко складывается в
несколько игроков на сервере.
*Что делать:* один общий проход (`ModSystem.PostUpdateEverything`) с индексом «свои
снаряды по типу», который читают все подсистемы; токены броска — не пересобирать каждый
тик, а обновлять по событию `OnKill`/подбор.

**F6 (P3). Микро-мусор в отрисовке.** `device.GetRenderTargets()` каждый кадр в
`FrostJetFx.RenderFire` возвращает новый массив; `SickleGlobalItem.PreDrawInInventory`
делает `ModContent.Request<Texture2D>` по строке на каждый слот каждый кадр (кэш tML спасает
от загрузки, но не от строкового поиска). Мелочь, но в UI заметно.

### 4.2. Сеть и мультиплеер

**F7 (P1). Заряд карамельки на выделенном сервере не расходуется.**
`SickleThrowProjectile.cs:239-240` уменьшает `SweetTicks` только при
`Projectile.owner == Main.myPlayer`. На dedicated server `Main.myPlayer` — не клиент,
поэтому у присоединившихся игроков серверная копия заряда **всегда полная**:
`CandyEaten` (`:151`) никогда не станет true, `CandyLureActive` — всегда true. Итог:
приманка, которая «должна кончиться за 10 секунд», на сервере работает бесконечно
(при этом `CandyCanePlayer.PostUpdate:86-90` на сервере продолжает заряд восстанавливать).
У хоста host-and-play всё работает, поэтому баг ловится только тестом с двумя клиентами.
*Что делать:* по образцу Frost — владелец считает заряд и публикует его пакетом
(или расходует сервер по `owner`-проверке), состояние — в `SyncPlayer`.

**F8 (P2). Полировка мечей и их Frost не синхронизированы вообще.**
`SwordPlayer.AddPolish` (`:275`) и `UpdateIceFrost` (`:292`) работают только у локального
игрока. Следствия: (а) у других игроков чужой Ice Blade всегда «шершавый», Frostbrand
не показывает накопленный жар; (б) множитель урона полировки
(`PolishDamageMult`) применяется в `SwordGlobalItem.Shoot` на клиенте владельца —
это client-authoritative урон, то есть расхождение с сервером и потенциальная
поверхность для читов. Для шкалы копья такая же проблема уже осознана и решена
(`SicklePlayer.SendFrost`), для мечей — нет.

**F9 (P2). Токены броска локальны.** `ThrownLockItem.Token` + `SicklePlayer.activeThrowTokens`
живут только в памяти клиента-владельца. Сценарии, которые надо проверить в игре:
смерть с брошенным серпом, выход и повторный вход, смена персонажа, рестарт сервера,
передача предмета в сундук/другому игроку. Симптом при рассинхроне — «предмет есть,
но пользоваться нельзя» или «предмет вернулся раньше снаряда».

**F10 (P3). Анимация подбора не синхронизируется покадрово.** `PickupAI`
(`SickleThrowProjectile.cs:1023`) у не-владельца каждый тик ставит `velocity = 0` без
`netUpdate`; владелец меняет скорость каждый тик. У наблюдателей подбор будет выглядеть
как «замерло и исчезло». Косметика, но легко чинится одним `netUpdate` каждые N тиков.

### 4.3. Совместимость и дизайн

**F11 (P2). Глобальная подмена `TextureAssets.Item` в `Mod.Load`.**
`FrostMelee.cs:67` (`OverrideWeaponTextures`) подменяет ванильные слоты IceSickle, IceBlade,
Frostbrand, CandyCaneSword, а `SickleTextures.UpdateView`/`IceBladeVisual` переключают их
дальше по шкале. Риски: (а) подмена делается один раз — если ассеты перезагрузятся
(ресурспак, смена графического профиля, reload), слот вернётся к ванили и мод об этом
не узнает, потому что нет обработчика перезагрузки; (б) если в сборке стоят сразу
FrostMelee + WoodSwordsOverhaul + ReaperMelee, порядок подмен одного и того же `ItemID`
решает, чей спрайт победит — сейчас никакой защиты от этого нет; (в) `Unload` возвращает
исходные `Asset<Texture2D>`, которые к тому моменту могут быть уже освобождены.
*Что делать:* подмену делать в `PostSetupContent` (после всех `Load`), кэш «кто уже
подменил» — по `ItemID` с приоритетом, и переприменять по событию перезагрузки ассетов.
Как минимум — проверить в игре с ресурспаком и с соседними модами серии.

**F12 (P2). Огонь навешивается на любой `Frostburn`/`Frostburn2` в мире.**
`FrostJetFx.HasFrostburn` (`:518`) не различает источник: враг, подожжённый Frostbrand
из другого мода, ледяной бронёй, ванильным оружием или вторым игроком, получит
frostmelee-визуал. Плюс хук `On_NPC.UpdateNPC_BuffApplyVFX` — MonoMod-хук по имени
и сигнатуре ванильного метода: при смене версии tModLoader/1.4.4 мод не загрузится
(или тихо потеряет визуал). Нужен маркер «наш источник» (свой скрытый баф или
`NPC.GivenName`-подобный признак через `GlobalNPC`-таблицу) и безопасная регистрация хука.

**F13 (P3). `FrostDrainFx` индексирует NPC без проверки диапазона.**
`FrostDrainFx.cs:91` и `:131`: `Main.npc[(int)Projectile.ai[0]]`. Спавн защищён
(`Play` проверяет `target != null`), но `ai[0]` приходит из сети; в `FrostJetFx:628`
такая проверка есть (`< 0 || >= Main.maxNPCs`) — здесь нет. Один битый пакет/некорректный
спавн = исключение в AI на всех клиентах. Привести к общему виду.

**F14 (P3). Отладочные глобальные переключатели.** `SickleSprite.ShaftHits` (`:102`) —
публичный `static bool`, который меняет поведение хитбокса для всех и нигде не
сбрасывается в `Unload`; `SickleArcProjectile.DebugHitbox`/`SwordArcProjectile.DebugHitbox`
тоже публичные статики. Вынести в `#if DEBUG` или в клиентский конфиг, и сбрасывать в `Unload`.

**F15 (P3). Дублирование SetDefaults.** `Aisberg.SetDefaults` (`:20-45`) повторяет то, что
уже делает `SwordGlobalItem.SetDefaults` (`shoot`, `shootsEveryUse`, `noUseGraphic`).
Безвредно, но при следующем изменении движка мечей легко забыть одну из двух копий.
Там же: статический реестр `SwordTypes.AisbergType` нигде не сбрасывается в `Unload`.

### 4.4. Гигиена репозитория и документация

**F16 (P2). Мусор в git.** Отслеживается 21 `.bak` (версии снарядов и рибонов), 21 файл
`bin/obj` со старой сборкой, `_backup_tmods/*.tmod`, `HardcoreMeleeMode_backup_*.tar.gz`,
`Gungnir_(demo) (1).gif` (836 КБ). В `FrostMelee/obj/FrostMelee.csproj.nuget.g.props`
лежат абсолютные пути `C:\Users\user\.nuget\packages\` — машино-специфичные данные в истории.
`.gitignore` уже содержит `**/bin`, `**/obj`, `*.bak`, `*.tmod`, `*.tar.gz`, но **уже
отслеживаемые файлы игнором не снимаются** — нужен отдельный коммит `git rm --cached`.

**F17 (P3). Половина спрайтов не используется.** 22 из 45 PNG нигде не упоминаются:
`Items/AmarokIce1..14` (есть собранный `AmarokIceStrip`), `Items/Amarok_FROZEN(projectile)`,
`Items/IceSpearProjectile`, `Textures/Effects/IceCoat`, `IceSpike`, `IceSpike1`, `IceSpike2`
(живые — `*-export`), `Textures/Items/IC_Spear_Death`, `AmarokShardProjectile_preview`.
Плюс имена с пробелами и скобками (`Candy Cane Sword gray.png`,
`Amarok_FROZEN(projectile).png`) — работают, но это лишний источник ошибок на других ОС.

**F18 (P2). Локализация.** `en-US_Mods.FrostMelee.hjson` содержит **русский** текст
(все `Configs.*`), а `ru-RU` держит эти же ключи закомментированными (`// Label: ...`),
поэтому подписи настроек берутся из `[Label]`/`[Tooltip]` в коде — тоже по-русски.
Практический результат: у англоязычного игрока настройки мода по-русски. Плюс три ключа

## 5. Что проверить в игре (чеклист)

Статический анализ не заменяет игру; ниже — то, что закрывает самые «дорогие» риски.

1. **FPS в бою:** 5+ горящих врагов Frostbrand'ом в снежном биоме; замер с модом и без
   (F1–F3). Особенно — на сервере с 2–3 игроками.
2. **Dedicated server, клиент (не хост):** бросить леденец, стоять 20+ секунд — приманка
   должна кончиться (F7).
3. **Dedicated server, два клиента:** у второго игрока чужой Ice Blade/Frostbrand —
   виден ли иней, совпадает ли урон (F8).
4. **Смерть/выход с брошенным серпом**, вход обратно, рестарт сервера (F9).
5. **Ресурспак** поверх мода + смена настроек графики: не «отваливаются» ли спрайты
   копья/мечей (F11).
6. **FrostMelee + WoodSwordsOverhaul + ReaperMelee одновременно** (F11, F20).
7. **Чужой Frostburn:** поджечь врага ванильным Frostburn (не нашим мечом) — не должен
   получать наш огонь, если это не задумано (F12).
8. **Северный полюс:** сейчас ванилла, приёмы не работают — убедиться, что тултипы
   не обещают несуществующего (F19).
9. **Английский язык клиента:** настройки мода и тултипы (F18).
10. **Смена префикса/размера оружия** (легендарный, большой) — геометрия урона должна
    масштабироваться вместе со спрайтом (это уже покрыто масками, но проверить стоит).

```sh
# данные масок и тесты (нужен Pillow)

git status --short
git ls-files | grep -E '\.bak$|/bin/|/obj/|\.tmod$'
```

## 9. Итоговая оценка

| Направление | Оценка | Почему |
|---|---|---|
| Геймплей и проработка механик | 9/10 | приёмы, ресурсы, визуал продуманы до деталей, решения зафиксированы в документах |
| Архитектура данных (геометрия, маски) | 9/10 | CPU-маски + генератор + тесты, единый источник правды |
| Производительность | 4/10 | три «тяжёлых» цикла в кадровых/потиковых хуках, логи в горячем пути |
| Мультиплеер | 5/10 | Frost копья синхронизирован хорошо, мечи/карамель/токены — нет |
| Совместимость | 6/10 | глобальная подмена текстур и MonoMod-хук без страховки |
| Качество кода | 7/10 | читаемо и документировано, но длинные методы и дублирование с ReaperMelee |
| Гигиена репозитория | 3/10 | `.bak`, `bin/obj`, абсолютные пути, ~половина спрайтов не используется |
| Проверяемость | 4/10 | тесты есть только для данных масок, сборка и игра не автоматизирована |

Проект ближе к «продукту», чем к прототипу: механики доведены, документация подробная.
Основные вложения на следующем шаге — не новые приёмы, а **профиль производительности
в бою**, **сетевой слой для мечей/карамельки** и **чистка репозитория**.
